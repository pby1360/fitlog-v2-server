# FitLog 개발 루프

1. **범위 확인.** 작업할 코드 저장소의 루트 [`AGENTS.md`](../../../AGENTS.md)를 읽는다. 원격 `main`과 현재 작업 트리를 대조하고 독립 작업 브랜치를 사용한다. 다른 저장소에 의존하는 경우 해당 계약과 관련 PR을 확인한다.
2. **요구사항과 검증 계획.** 공식 문서의 대상 PRD·Tech Spec, 현재 상태, 백로그와 관련 ADR·Issue를 읽는다. 요청 범위, 수용 기준별 예상 결과·검증 방법, 영향을 받는 코드 경로를 짧게 정리한다. 공통 검증 명령은 저장소의 `AGENTS.md`를 따른다. 필요한 설계 변경은 이유·대안·영향을 제시하고 구현 전에 사용자 승인을 기다린다. 영향받는 Tech Spec·API·아키텍처와 현황·백로그·개발 이력을 검증 계획에 넣는다.
## 승인 대기·차단 진단 (읽기 전용 사전 조사)

범위 확인과 요구사항·검증 계획(1~2단계)에서 필수 정보나 승인이 부족하면 승인되지 않은 구현을 시작하는 대신 아래 사전 조사를 수행한다. 이는 개발 실행을 허용하는 예외가 아니며, Docs의 [승인 대기 조사 규칙](https://github.com/pby1360/fitlog-v2-docs/blob/main/operations/DEVELOPMENT_WORKFLOW.md#승인-대기-중-차단-진단과-의사결정-지원)과 `TASKS.md` 상태 전이를 우선한다.

- `TECHNICAL`: 구현·테스트·계약 근거 부족. 기존 코드·PRD·ADR·Tech Spec·Issue·테스트·공개 자료를 읽어 확인 가능한 사실과 해결 경로를 정리한다.
- `POLICY`: 제품 범위 또는 운영 정책 미결정. 실제 구현과 초안의 차이, 권장안·대안·리스크를 제시하고 결정권자의 승인을 요청한다.
- `LEGAL`: 약관·개인정보 등 법적 문구 미승인. 공식 법령·작성 지침을 조사하고 **검토용** 초안을 작성하며 전문 검토가 필요한 항목을 구분한다.
- `APPROVAL`: 사용자 승인 미확보. 승인해야 할 최소 항목과 근거를 제시하되 실행하지 않는다.
- `ACCESS`: 공급자 콘솔·계약·운영 설정 등 접근 불가. 확인 불가라고 기록하고 확인 담당자 및 필요한 증빙을 요청한다. 리전·기간·설정을 추정으로 확정하지 않는다.
- `EXECUTION`: 기존 Cloud 실행·PR/선점 상태 확인 불가. 중복 실행·새 프롬프트·PR 생성을 멈추고 기존 Task ID, 브랜치, PR·CI, 실행 ID를 확인한다.

### 조사 절차와 재개 조건

1. 조사 시작 전 원격 Docs `main`의 `TASKS.md`와 대상 저장소의 열린 PR·커밋·CI를 읽어 해당 Task의 `PROPOSED`/`APPROVED`/`STARTING`/`IN_PROGRESS`/`PR_OPEN`/`BLOCKED` 상태를 대조한다. Cloud를 직접 확인할 수 없으면 **Cloud 실행 상태 미확인**으로 표시한다. 같은 Task가 이미 실행·검토·승인 대기 중이라면 별도 실행이나 PR을 제안하지 않는다.
2. 승인된 읽기 권한 내 코드·설계·이력·공식 자료를 조사하고 **확인된 사실, 추정, 미확인**을 분리한다. 허위 근거·미확인 설정의 단정은 금지한다. 조사 과정에서 운영 계정, DB, 비밀정보 또는 제한된 콘솔에 임의 접근하지 않는다.
3. 보고에는 Task ID·상태, 차단 유형, 근거 링크, 조사한 내용, 권장안과 대안/리스크, 사용자가 결정할 최소 질문, 승인 후 재개 단계, 남은 확인 제한을 포함한다. 새 사실이 없으면 같은 제안을 반복하지 않는다.
4. 사용자 명시적 승인 전에는 `TASKS.md` 선점/변경, 코드·공식 정책 문서 수정, 브랜치·PR 생성, Cloud 실행/재시작, 병합 또는 배포를 수행하지 않는다. 조사 요청은 구현·정책 승인으로 취급하지 않는다. 승인 후에도 Docs 승인·선점 규칙과 해당 SHA를 재확인하고 기존 실행의 중복 여부를 검증한 다음에만 구현 루프로 복귀한다.
5. 이 사전 조사는 아래 4~5단계의 **구현 후 테스트·수정 최대 5회**에 포함되지 않는다. 코드를 변경한 이후에는 기존 검증·리뷰·Draft PR·사용자 수동 병합 규칙을 그대로 적용한다.

**V1-01 예시:** 이용약관 및 개인정보처리방침 초안의 운영자·문의처·시행일·서비스 종료 고지, 접속 로그·백업 보존, 처리 위탁·국외 이전, 14세 미만 가입과 V1-11 선택 프로필을 조사 항목으로 정리한다. Web/Server 코드와 실제 확인 가능한 공개 근거를 대조하고 미확인 운영 설정은 결정을 요청한다. 승인된 최종 게시 문구 전에는 페이지 수정·PR·배포를 하지 않는다.

3. **최소 구현.** 승인된 범위에서 필요한 코드와 검증만 변경한다. 기존 계약과 테스트를 보존하고 기능에 상관없는 정리나 CI 변경을 섞지 않는다.
4. **실행·수정·재검증.** 첫 구현 뒤 검사 실행을 1회차로 센다. 각 회차에서 명령·결과·실패 원인·수정 사항을 남긴다. 검증이 실패하면 먼저 변경으로 인한 실패, 기존 실패, 환경 차단을 근거로 구분한다. 원인을 좁힌 뒤 범위 안에서 수정하고 관련 검사를 다시 실행한다. 운영 서비스나 배포 작업 없이 로컬·테스트 환경에서 진행한다.
5. **종료 판정.** 최대 5회차까지 진행한다. 성공 기준은 최종 변경분에 대한 수용 기준과 저장소의 기본 검증 통과다. 진단용 테스트 필터는 최종 전체 검사로 대체한다. 테스트 삭제·비활성화, 검사 제외, 기준 완화, 실행하지 않은 검사를 성공으로 기록하는 행위를 금지한다. 5회차에도 실패하거나 환경이 막히면 마지막 근거, 영향, 미검증 항목을 기록하고 완료 판정을 보류한다.
6. **자체 리뷰.** 기준 브랜치 대비 diff를 읽고 `git diff --check`를 확인한다. 수용 기준, 호환성, 정상·실패 경로, 보안과 테스트 범위를 대조한다. 리뷰 중 동작을 수정했다면 남은 회차에서 다시 검증하고 결과를 갱신한다.
7. **코드·문서 PR 제출.** 코드 Draft PR에 관련 문서·Issue, 변경 내용, 마지막 검증 회차와 실행 결과, 남은 실패를 적는다. 문서 영향이 있으면 독립 문서 브랜치에 Docs PR을 만들고 코드 저장소·PR 번호·기준 커밋을 적은 뒤 양쪽 PR을 연결한다. 같은 코드 PR의 기존 Docs PR과 날짜별 이력을 찾아 갱신한다. 문서 영향이 없으면 코드 PR에 근거를 남긴다. GitHub Actions의 PR 검사 결과를 확인해 기록하고 CI 생략 문구를 추가하지 않는다.
8. **병합과 동기화.** 수동 코드 병합은 사용자 승인을 기다린다. 승인된 구현 동기화 Docs PR은 같은 승인 범위의 정확한 문서 커밋을 병합 메시지로 지정한다. 요구사항·보안 정책·제품 범위·아키텍처 결정 문서는 별도 승인을 거친다. 병합 후 Docs 검사와 병합 결과를 확인한다. 승인된 기능 변경의 운영 배포는 GitHub Actions가 수행한다. 에이전트는 운영 배포나 수동 워크플로를 실행하지 않는다.
