# FitLog 개발 루프

1. **범위 확인.** 작업할 코드 저장소의 루트 [`AGENTS.md`](../../../AGENTS.md)를 읽는다. 원격 `main`과 현재 작업 트리를 대조하고 독립 작업 브랜치를 사용한다. 다른 저장소에 의존하는 경우 해당 계약과 관련 PR을 확인한다.
2. **요구사항과 검증 계획.** 공식 문서의 대상 PRD·Tech Spec, 현재 상태, 백로그와 관련 ADR·Issue를 읽는다. 요청 범위, 수용 기준별 예상 결과·검증 방법, 영향을 받는 코드 경로를 짧게 정리한다. 공통 검증 명령은 저장소의 `AGENTS.md`를 따른다. 필요한 설계 변경은 이유·대안·영향을 제시하고 구현 전에 사용자 승인을 기다린다. 영향받는 Tech Spec·API·아키텍처와 현황·백로그·개발 이력을 검증 계획에 넣는다.
3. **최소 구현.** 승인된 범위에서 필요한 코드와 검증만 변경한다. 기존 계약과 테스트를 보존하고 기능에 상관없는 정리나 CI 변경을 섞지 않는다.
4. **실행·수정·재검증.** 첫 구현 뒤 검사 실행을 1회차로 센다. 각 회차에서 명령·결과·실패 원인·수정 사항을 남긴다. 검증이 실패하면 먼저 변경으로 인한 실패, 기존 실패, 환경 차단을 근거로 구분한다. 원인을 좁힌 뒤 범위 안에서 수정하고 관련 검사를 다시 실행한다. 운영 서비스나 배포 작업 없이 로컬·테스트 환경에서 진행한다.
5. **종료 판정.** 최대 5회차까지 진행한다. 성공 기준은 최종 변경분에 대한 수용 기준과 저장소의 기본 검증 통과다. 진단용 테스트 필터는 최종 전체 검사로 대체한다. 테스트 삭제·비활성화, 검사 제외, 기준 완화, 실행하지 않은 검사를 성공으로 기록하는 행위를 금지한다. 5회차에도 실패하거나 환경이 막히면 마지막 근거, 영향, 미검증 항목을 기록하고 완료 판정을 보류한다.
6. **자체 리뷰.** 기준 브랜치 대비 diff를 읽고 `git diff --check`를 확인한다. 수용 기준, 호환성, 정상·실패 경로, 보안과 테스트 범위를 대조한다. 리뷰 중 동작을 수정했다면 남은 회차에서 다시 검증하고 결과를 갱신한다.
7. **코드·문서 PR 제출.** 코드 Draft PR에 관련 문서·Issue, 변경 내용, 마지막 검증 회차와 실행 결과, 남은 실패를 적는다. 문서 영향이 있으면 독립 문서 브랜치에 Docs PR을 만들고 코드 저장소·PR 번호·기준 커밋을 적은 뒤 양쪽 PR을 연결한다. 같은 코드 PR의 기존 Docs PR과 날짜별 이력을 찾아 갱신한다. 문서 영향이 없으면 코드 PR에 근거를 남긴다. GitHub Actions의 PR 검사 결과를 확인해 기록하고 CI 생략 문구를 추가하지 않는다.
8. **병합과 동기화.** 수동 코드 병합은 사용자 승인을 기다린다. 승인된 구현 동기화 Docs PR은 같은 승인 범위의 정확한 문서 커밋을 병합 메시지로 지정한다. 요구사항·보안 정책·제품 범위·아키텍처 결정 문서는 별도 승인을 거친다. 병합 후 Docs 검사와 병합 결과를 확인한다. 승인된 기능 변경의 운영 배포는 GitHub Actions가 수행한다. 에이전트는 운영 배포나 수동 워크플로를 실행하지 않는다.
